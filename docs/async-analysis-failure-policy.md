# 비동기 분석 실패 처리 정책 초안

## 1. 문서 목적

비동기 분석 Job/Queue 구조에서는 크롤링, Queue 메시지 처리, DB 저장, RTI 분석 등 여러 단계에서 실패가 발생할 수 있다.

사용자는 분석 요청 직후 결과를 받는 대신 Job 상태를 통해 완료 여부를 확인하므로, 실패 처리 기준이 없으면 프론트가 계속 대기 상태로 보이거나 백엔드에서 실패 원인을 추적하기 어려울 수 있다.

따라서 실제 구현 전에 다음 항목을 명확히 정의할 필요가 있다.

- 어떤 경우를 실패로 볼지
- Job 상태를 어떻게 바꿀지
- 실패 원인을 어디에 저장할지
- 프론트에는 어떤 메시지를 보여줄지
- 재시도를 할지

이 문서는 `product_analysis_job.status = FAILED` 처리 기준과 실패 원인 저장 방식을 협의하기 위한 초안이다. 현재 코드 동작이나 DB schema 변경을 포함하지 않는다.

## 2. 기본 처리 원칙 후보

- 분석을 더 이상 정상적으로 진행할 수 없는 오류는 원칙적으로 Job을 `FAILED`로 변경한다.
- 내부 디버깅용 오류 정보와 프론트 사용자 노출 메시지는 분리한다.
- 네트워크나 외부 시스템의 일시적 오류는 재시도 대상으로 검토한다.
- 입력값 누락, 지원하지 않는 값 등 재시도로 해결되지 않는 오류는 즉시 실패 처리하는 방향을 검토한다.
- 일부 단계가 성공했더라도 최종 분석 결과를 신뢰할 수 없다면 Job 완료로 처리하지 않는다.
- Job 상태 업데이트 자체가 실패한 경우에는 로그와 별도의 모니터링 수단으로 반드시 추적할 수 있어야 한다.

## 3. 예상 실패 지점

1. Redis Queue 메시지 형식 오류
2. `jobId` 누락
3. `productUrl` 누락
4. 지원하지 않는 mall/platform
5. 크롤링 요청 실패
6. 리뷰 0개 수집
7. raw JSON 저장 실패

9. reviews DB insert 실패
10. RTI 분석 실패
11. `review_trust_scores` 저장 실패
12. Job 상태 업데이트 실패

## 4. 실패 케이스별 처리 후보

아래 내용은 확정 정책이 아닌 팀 협의용 후보이다. `error_message` 컬럼 및 재시도 관련 정보는 현재 schema에 없으므로 실제 저장을 전제로 하지 않는다.

| 실패 케이스 | Job 상태 후보 | 내부 `error_message` 예시 | 재시도 후보 | 프론트 메시지 |
| --- | --- | --- | --- | --- |
| Redis Queue 메시지 형식 오류 | 식별 가능한 `jobId`가 있으면 `FAILED`. 식별할 수 없으면 Job 갱신 없이 오류 로그 기록 | `Invalid queue message format: required payload structure is not satisfied` | 불가. 동일 메시지 재처리로 해결되기 어려움 | 내부 형식 오류는 숨기고 일반 오류 메시지로 단순화 |
| `jobId` 누락 | 대상 Job을 식별할 수 없어 `FAILED` 갱신이 어려움. 오류 로그 및 모니터링 필요 | `Missing required field: jobId` | 불가 | 일반 오류 메시지로 단순화. 사용자 요청과 연결할 방법 별도 검토 |
| `productUrl` 누락 | `jobId`가 있으면 `FAILED` | `Missing required field: productUrl` | 불가 | `상품 URL 정보가 올바르지 않습니다.` |
| 지원하지 않는 mall/platform | `FAILED` | `Unsupported mall/platform: {mall}` | 불가 | `지원하지 않는 상품 URL입니다.` |
| 크롤링 요청 실패 | 재시도 종료 후 `FAILED` | `Crawler request failed: {error_type/status_code}` | 가능. 네트워크 오류, 타임아웃, 일시적 외부 장애 등으로 제한 검토 | `리뷰를 가져오지 못했습니다.` |
| 리뷰 0개 수집 | `FAILED`, `DONE`, 별도 상태 중 협의 필요 | `No reviews collected for product` | 원인이 일시적 크롤링 실패인지 실제 리뷰 없음인지에 따라 결정 | `수집된 리뷰가 없습니다.` 등 별도 메시지 검토 |
| raw JSON 저장 실패 | `FAILED` | `Failed to save raw crawl result: {storage_error}` | 저장소의 일시적 오류인 경우 가능 | 일반 오류 메시지로 단순화 |
| converter 실패 | `FAILED` | `Failed to convert raw review data: {conversion_error}` | 데이터 형식 문제는 불가. 일시적 의존성 오류만 제한적으로 가능 | 일반 오류 메시지로 단순화 |
| reviews DB insert 실패 | `FAILED` | `Failed to insert reviews: {db_error}` | DB 연결, 타임아웃 등 일시적 오류는 가능 | 일반 오류 메시지로 단순화 |
| RTI 분석 실패 | `FAILED` | `RTI analysis failed: {analysis_error}` | 모델/API 타임아웃이나 일시적 장애는 가능. 입력 데이터 오류는 불가 | `분석 중 오류가 발생했습니다. 잠시 후 다시 시도해주세요.` |
| `review_trust_scores` 저장 실패 | `FAILED` | `Failed to save review trust scores: {db_error}` | DB 연결, 타임아웃 등 일시적 오류는 가능 | 일반 오류 메시지로 단순화 |
| Job 상태 업데이트 실패 | 목표 상태 반영 실패. 별도 로그, 모니터링 및 보정 절차 필요 | `Failed to update job status to {target_status}: {db_error}` | 가능. 단, 중복 처리와 상태 역전 방지 필요 | 프론트가 계속 대기할 수 있으므로 타임아웃 또는 상태 보정 정책 필요 |

### 오류 메시지 기록 시 주의사항

- 비밀번호, 인증 토큰, DB 접속 정보 등 민감정보를 저장하지 않는다.
- 전체 리뷰 원문이나 과도하게 큰 payload를 저장하지 않는다.
- 오류가 발생한 단계와 오류 유형을 식별할 수 있는 수준으로 기록한다.
- DB 오류 원문이나 stack trace를 사용자에게 직접 노출하지 않는다.
- 메시지 길이 제한과 보관 기간은 컬럼 추가 검토 시 함께 정한다.

## 5. `error_message` 컬럼 필요성

현재 `product_analysis_job`에는 `FAILED` 상태가 있지만 실패 원인을 저장할 `error_message` 컬럼이 없다.

AI 파트 의견은 다음과 같다.

> `FAILED` 상태만으로는 원인 파악이 어렵기 때문에 `error_message` 컬럼 추가를 검토할 필요가 있다.

`error_message`가 있으면 Job 단위의 실패 지점 확인, 운영 장애 분석, 사용자 문의 대응, 재시도 대상 판별에 도움이 될 수 있다.

다만 다음 사항은 팀 협의가 필요하다.

- 컬럼 추가 여부와 자료형 및 최대 길이
- 내부 오류 코드와 상세 메시지를 하나의 컬럼에 저장할지 여부
- 실패 후 재시도에 성공하면 기존 오류 메시지를 유지할지 초기화할지 여부
- 민감정보 제거 기준
- 오류 메시지 보관 기간

이 문서에서는 필요성만 기록하며 DB schema는 변경하지 않는다.

## 6. 리뷰 0개 수집 처리

리뷰가 0개 수집된 경우는 다음 두 상황을 구분할 필요가 있다.

- 상품에 실제로 등록된 리뷰가 없는 경우
- 크롤링 차단, 페이지 구조 변경, 응답 오류 등으로 리뷰를 가져오지 못한 경우

상태 처리 후보는 다음과 같다.

| 후보 | 처리 방식 | 장점 | 고려사항 |
| --- | --- | --- | --- |
| A안 | `FAILED` | 분석 결과가 없다는 사실을 명확하게 표현하고 기존 상태값을 유지할 수 있음 | 실제로 리뷰가 없는 정상 상품도 실패로 분류될 수 있음 |
| B안 | `DONE` + `review_count = 0` | 실제 리뷰가 없는 경우를 정상 처리할 수 있고 기존 상태값을 유지할 수 있음 | 크롤링 실패를 정상 완료로 오인하지 않도록 원인 구분이 필요함 |
| C안 | `DONE_WITH_NO_REVIEWS` | 결과 없음 상태를 명확하게 구분할 수 있음 | 상태값과 프론트 분기, API 계약이 복잡해짐 |

AI 파트 기준으로 초기 MVP에서는 상태값을 단순하게 유지하기 위해 A안 또는 B안을 우선 검토할 수 있다. 가능하다면 크롤러가 "실제 리뷰 없음"과 "수집 실패"를 구분할 수 있는지도 함께 확인해야 한다.

## 7. 재시도 정책 후보

크롤링 요청, 외부 RTI 분석 요청, DB 연결 등은 일시적으로 실패할 수 있으므로 재시도 정책을 검토할 필요가 있다.

| 후보 | 장점 | 고려사항 |
| --- | --- | --- |
| 재시도 없음 | 구현과 상태 관리가 단순함 | 일시적 장애도 즉시 최종 실패로 처리됨 |
| 1회 재시도 | 복잡도를 크게 높이지 않고 일시적 오류를 일부 흡수할 수 있음 | 재시도 간격과 중복 저장 방지 기준 필요 |
| 최대 3회 재시도 | 일시적 외부 장애에 대한 복원 가능성이 높음 | 처리 시간 증가, Queue 적체, 중복 처리 및 상태 관리 복잡도 증가 |

재시도 대상으로 검토할 수 있는 실패는 다음과 같다.

- 크롤링 네트워크 오류 및 타임아웃
- 외부 API의 일시적 오류
- DB 연결 오류 및 타임아웃
- 일시적인 저장소 접근 오류

재시도하지 않는 방향을 검토할 수 있는 실패는 다음과 같다.

- 필수 필드 누락
- 지원하지 않는 mall/platform
- 잘못된 데이터 형식
- 변환할 수 없는 고정 입력 데이터

다음 항목은 팀 협의가 필요하다.

- `retry_count` 컬럼이 필요한지
- 어떤 실패만 재시도할지
- 재시도 횟수와 간격
- 고정 간격 또는 exponential backoff 적용 여부
- 재시도 중 Job 상태를 어떻게 표현할지
- 재시도 시 중복 크롤링 및 중복 DB insert를 어떻게 방지할지
- 재시도 후에도 실패하면 `FAILED`로 확정할지

현재 schema에 없는 `retry_count`는 이 문서에서 협의 필요 항목으로만 기록한다.

## 8. 프론트 노출 메시지

프론트에는 상세한 내부 오류를 그대로 보여주기보다 사용자가 이해하고 다음 행동을 결정할 수 있는 메시지를 제공해야 한다.

사용자 메시지 예시는 다음과 같다.

- `분석 중 오류가 발생했습니다. 잠시 후 다시 시도해주세요.`
- `리뷰를 가져오지 못했습니다.`
- `지원하지 않는 상품 URL입니다.`
- `수집된 리뷰가 없습니다.`

내부 `error_message`와 사용자 노출 메시지는 다음 이유로 분리할 필요가 있다.

- DB 오류, stack trace, 내부 서비스명 등 불필요한 기술 정보 노출 방지
- 인증정보나 내부 경로 등 민감정보 노출 방지
- 사용자에게 일관되고 이해하기 쉬운 문구 제공
- 내부 오류 유형이 변경되어도 프론트 메시지 계약 유지

프론트 메시지 전달 방식은 오류 코드 기반 매핑 또는 백엔드의 사용자 메시지 필드 제공 방식 등을 협의할 수 있다.

## 9. 로그와 디버깅

실패 원인을 추적하려면 다음 정보를 Job 단위로 확인할 수 있는 것이 좋다.

- `job_id`
- `mall`
- `product_id`
- `product_url`
- `status`
- `error_message`
- `created_at`
- `updated_at`
- `started_at`
- `finished_at`
- `retry_count`

로그에는 각 처리 단계의 시작, 성공, 실패와 소요 시간을 함께 남기는 방안도 검토할 수 있다. `job_id`를 공통 식별자로 사용하면 Queue Worker, 크롤러, DB 저장, RTI 분석 로그를 연결하기 쉽다.

현재 schema에 없는 `error_message`, `started_at`, `finished_at`, `retry_count` 등은 이 문서에서 협의 필요 항목으로만 기록하며 schema를 변경하지 않는다.

## 10. 팀 협의 필요 항목

- `error_message` 컬럼 추가 여부
- `retry_count` 컬럼 추가 여부
- `started_at` / `finished_at` 컬럼 추가 여부
- 리뷰 0개 수집 상태 처리
- 프론트 사용자 메시지 형식
- 어떤 실패를 재시도할지
- 재시도 횟수, 간격 및 최종 실패 확정 기준
- FastAPI가 DB에 직접 `FAILED`를 기록할지
- Spring API를 통해 `FAILED`를 기록할지
- `jobId`가 없는 Queue 메시지의 추적 및 처리 방식
- Job 상태 업데이트 실패 시 보정 및 모니터링 방식
- 내부 오류 코드와 사용자 메시지의 매핑 방식

특히 `FAILED` 기록 주체는 트랜잭션 경계, 서비스 간 책임, DB 접근 권한, 장애 시 의존성 등을 고려해 결정해야 한다.

## 11. 결론

비동기 분석 구조에서 실패 처리 정책이 없으면 프론트는 완료되지 않은 Job을 계속 대기 상태로 표시할 수 있고, 백엔드는 실패 원인을 추적하거나 재처리 대상을 판단하기 어렵다.

따라서 실제 Redis Worker나 크롤러를 구현하기 전에 실패 케이스, Job 상태 처리, 오류 정보 저장, 사용자 메시지, 재시도 정책을 먼저 합의하는 것이 안전하다.

이 문서는 협의를 위한 초안이며 코드, API endpoint, DB schema, Redis/Worker 및 크롤러 구현을 변경하지 않는다.
