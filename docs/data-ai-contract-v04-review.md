# Data/AI v0.4 계약 차이·질문·샘플 점검표

- 크롤링/Data 파트의 실제 입력 샘플·최종 전달 명세는 아직 받지 않은 상태다.

PDF는 목표 계약(Target Contract) 검토본이라고 명시한다(2·10쪽).
이 문서는 PDF 제안, 현재 구현, 미확정 질문을 구분한다. 원본 PDF를 저장소에 복사하거나
기존 API·점수 공식·DB·SSE 동작을 변경하지 않는다.

## 1. 먼저 확인할 세 가지

1. **저장 책임:** Data가 result DB를 관리하는 것과 AI 자체 복구용 저장을 유지하는 것은 별도 결정이다.
   PDF의 “AI가 result DB에 직접 저장하지 않는다”가 둘 중 어디까지 뜻하는지 확인한다.
2. **분석 정책:** 근거 부족을 `unavailable`로 처리하면 현재 기본값·고정 가중치 계산과 달라진다.
   응답 포장만 바꿔 같은 알고리즘이라고 간주하지 않는다.
3. **실제 입력 경계:** 크롤러 원본이 아니라 **Data가 정규화한 뒤 AI로 보내는 JSON**이 필요하다.
   원본만 받으면 실제 연동 계약을 검증할 수 없다.

## 2. 구조·통신 차이

| 항목 | 현재 브랜치 | PDF 제안 / 미확정 사항 |
| --- | --- | --- |
| 기본 분석 | `POST /api/v1/analyze`가 리뷰를 받아 저장·분석·결과 저장 후 JSON 응답 | 정규화 리뷰를 AI에 전달하고 결과 반환. URL·인증·timeout은 미명시 |
| 수집 | 기본 API는 수집하지 않음. 실험 경로는 외부 크롤러 SSE를 직접 구독 | Data가 쇼핑몰 API 호출·수집·정규화 담당 (2쪽) |
| 저장 | AI 자체 SQLite `ai_analysis_jobs`에 요청·결과 저장 | Data가 reviews/result/jobs 저장. AI 자체 백업 허용 여부는 확인 필요 |
| 완료 통지 | 기본 API는 최종 결과 응답. 실험 SSE는 저장 후 `result` 이벤트 | SSE·202 접수·콜백·polling 여부는 이 PDF만으로 확정할 수 없음 |

## 3. 요청 차이 (PDF 3쪽)

| 항목 | 현재 기본 분석 API | PDF 목표 / 확인 질문 |
| --- | --- | --- |
| `platform` | 없음. 추가 필드 금지로 요청 시 422 | 최상위 필수. 허용 이름·대소문자 규칙 확인 |
| `product_id` | 최상위 비어 있지 않은 문자열 | 필수 원본 식별자. 플랫폼 간 충돌과 앞자리 0 보존 확인 |
| `reviews` | 1개 이상 필수 | 목록 필수. 빈 목록·최대 개수·요청 크기는 별도 확인 |
| `review_id` | 리뷰별 필수 문자열 | 필수 원본 식별자. 유일성 범위와 중복 처리 확인 |
| `content` | 길이 1 이상 필수 문자열 | 필수 본문. 공백만 있는 값·삭제 리뷰·HTML·최대 길이 정책 확인 |
| `user_id` | 필수 | 최소 요청에 없음. 가짜 작성자 ID를 만들어 채우지 않기 |
| `review_date` / `written_at` | `review_date` 필수 문자열, `written_at` 추가 불가 | `written_at` 선택. 누락/null/날짜 형식/시간대 확인 |
| `rating` | 생략 시 5, 엄격한 정수 1~5 | 선택이며 현재 text baseline에 미사용. 소수점·범위·null 허용 여부 확인 |
| 행동 근거 | 구매 여부 unknown, 일일 작성 수 1 등 기본값 존재 | 구매 인증·계정 생성·빈도 등 추가 근거가 있을 때만 확장 가능 |
| 네트워크 근거 | `similar_review_count` 입력, 생략 시 0 | 동일 상품 리뷰 묶음을 비교. 묶음 범위·최소 리뷰 수·담당 분석기 확인 |

근거 코드: [AnalysisReview / AnalyzeRequest](../app/api/schemas.py).
**PDF 요청 예시는 현재 기본 API에 그대로 호환되지 않는다:** 최상위 `platform`과 리뷰의
`written_at`은 허용되지 않고, `user_id`와 `review_date`는 빠져 있어 422 대상이다.

현재 [실험 크롤러 매핑](../app/integrations/crawler_mapping.py)은 별도 경로다.
승인 플래그를 켜면 `platform:review_id`를 만들고 누락 신호에 기존 DTO 기본값을 사용한다.
이를 PDF의 원본 ID 반환·unavailable 정책과 동일한 매핑으로 재사용해서는 안 된다.

## 4. 응답·점수 차이 (PDF 4~9쪽)

| 항목 | 현재 구현 | PDF 목표 |
| --- | --- | --- |
| 최상위 | `product_id`, `results` | `platform`, `product_id`, `results`; `review_count`는 선택 |
| RTI | 정수 `rti`, 문자열 `level`; 가용성 필드 없음 | `rti_available`, float 또는 null인 `rti`, 문자열 또는 null인 `level` |
| signals | text/behavior/network 각각 정수 | 각각 `available`, `score: float 또는 null`, `unavailable_reasons: string[]` |
| reasons | `code`, `message` | `source` 추가; 근거가 없으면 빈 배열 가능 |
| 추가 반환 | content/author/date/input_features 포함 | 최소 계약에 없음. 추가 필드 허용 여부는 확인 필요 |
| 운영 필드 | 현재 응답과 팀원 응답 구조가 서로 다름 | used_signals/applied_weights/analysis_review_id/product_key 등은 필수 계약에서 제외 |

PDF에서 명시하는 의미:

- 높은 점수는 더 높은 신뢰도 방향이다. 내부 모델 위험 확률을 그대로 신뢰 점수로 반환하지 않는다.
- 근거 없음은 위험 점수 0이나 안전 점수 100이 아니라 `available=false`, `score=null`이다.
- `unavailable_reasons`는 계산 불가 이유, `reasons`는 분석에서 생성한 판단 근거다.
- 사용 가능한 신호가 없으면 `rti_available=false`, `rti=null`, `level=null`이다.
- 비교 리뷰 부족·행동 근거 부족은 정상적인 unavailable 상태일 수 있다.
  네트워크 장애·모델 실행 오류까지 동일하게 숨겨도 된다는 뜻은 아니다.

현재 [통합 분석 함수](../ai/analysis.py)는 세 점수에 0.4/0.35/0.25를 적용하고 Python `round`로
정수화한다. 등급은 50 미만 danger, 80 미만 warn, 나머지 safe다.
PDF는 일부 신호만으로 RTI를 계산할 수 있다고 설명하지만 **정확한 재가중치, 반올림, 최소 신호 조건은
제시하지 않는다.** 예시 RTI 82.4를 계산 공식이나 고정 기대값으로 사용하지 않는다.

## 6. 실제 입력 샘플 요청 목록

API 키·쿠키·토큰은 제외하고, 개인 식별정보는 익명화한 샘플을 요청한다.
익명화하더라도 동일 작성자·리뷰의 연결 관계와 데이터 타입은 검증할 수 있게 유지한다.

- [ ] 플랫폼별 일반 리뷰 묶음: Data가 실제 AI에 전송할 전체 JSON.
- [ ] 같은 샘플의 크롤러 원본 및 정규화 매핑표: 이름 변경·삭제·기본값 주입 여부.
- [ ] 선택 필드 누락과 명시적 null 사례. 빈 문자열·0·false와 구분.
- [ ] 동일 상품 리뷰 1건과 여러 건, 유사/반복 본문이 포함된 사례.
- [ ] 확보 가능하다면 행동 근거가 있는 사례와 없는 사례. 없으면 확보 불가라고 명시.
- [ ] 리뷰 0건·중복 ID·변경된 리뷰·삭제/빈 본문 처리 사례.
- [ ] 서로 다른 플랫폼에 같은 숫자 ID가 있는 사례, 앞자리 0이 있는 문자열 ID.
- [ ] 소수점 별점·누락 날짜·시간대 포함/미포함·이모지/줄바꿈 본문 사례.
- [ ] 예상 1회 리뷰 수·최대 본문 길이·최대 요청 크기·동시 요청 수.
- [ ] 정상 결과와 실패 결과를 Data가 어떻게 매칭·저장할지 기대 예시.

실제 확보되지 않는 엣지 케이스는 이후 합성 테스트로 보완하되, 실제 원천 데이터라고 표시하지 않는다.

## 7. 샘플 수령 후 점검 순서

1. **출처 구분:** 크롤러 원본인지 Data 정규화본인지, 플랫폼·스키마 버전 확인.
2. **형식 검증:** 필드명·타입·필수 여부·누락/null·범위·날짜/시간대·크기 확인.
3. **식별자 검증:** platform/product_id/review_id 보존, 중복·충돌·재요청 매칭 확인.
4. **분석 단위 검증:** 같은 상품 묶음인지, 비교 가능한 리뷰가 충분한지, 부분 배치인지 확인.
5. **근거 검증:** 실제 관측과 Data가 보정한 기본값을 구분. 없는 근거를 만들어 점수화하지 않기.
6. **목표 응답 테스트 설계:** 가용/비가용 신호, 모든 신호 부재, 빈 reasons, ID 반환·개수 일치 확인.
7. **정책 승인 후 비교 실행:** 기존 API 회귀 테스트를 유지하고 새 계약 결과를 별도로 검증.
   스키마 준비 단계에서 운영 API나 가중치를 덮어쓰지 않기.
8. **연동 검증:** HTTP 실패·timeout·재시도·저장 실패·연결 끊김을 합의된 계약으로 확인.
