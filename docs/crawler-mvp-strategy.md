# Crawler MVP 전략

## 문서 목적

Re:view 프로젝트에서 크롤링은 리뷰 신뢰도 분석에 필요한 원천 데이터를 수집하는 수단이다.

네이버 및 쇼핑몰 리뷰 크롤링은 동적 로딩, 내부 API 변경, 요청 차단, pagination, 상품별 데이터 구조 차이 등의 변수가 있어 v1에서 완성형으로 구현하기 어렵다.

따라서 v1에서는 크롤러의 범위를 분석 파이프라인 검증에 필요한 MVP 수준으로 제한하고, raw JSON부터 saved RTI 저장까지의 흐름을 안정적으로 연결하는 것을 우선한다.

## 1. 크롤링의 역할

크롤링은 RTI 모델이나 분석 로직 자체가 아니라, RTI 분석에 필요한 리뷰 원천 데이터를 수집하는 역할을 한다.

전체 흐름은 다음과 같다.

```text
productUrl
→ crawler
→ raw JSON
→ converter
→ reviews DB insert
→ RTI analysis
→ review_trust_scores 저장
```

크롤러의 출력은 기존 converter가 처리할 수 있거나, 명확한 변환 규칙을 통해 기존 파이프라인에 연결할 수 있는 형식이어야 한다.

## 2. 크롤러 구현 난이도

아래와 같은 이유로 크롤러를 v1에서 완성형으로 구현하기 어렵다.

```text
- 쇼핑몰 페이지가 동적으로 로딩됨
- 내부 리뷰 API가 변경될 수 있음
- referer/header 조건이 필요할 수 있음
- 요청 차단 가능성이 있음
- pagination 구조가 상품/플랫폼마다 다를 수 있음
- 이미지 리뷰/텍스트 리뷰 구조가 다를 수 있음
```

쇼핑몰의 페이지 및 내부 API는 프로젝트가 통제하는 인터페이스가 아니므로 예고 없이 변경될 수 있다. 따라서 특정 시점에 동작하는 수집 코드가 운영 환경에서도 지속해서 동작한다고 보장하기 어렵다.

## 3. v1 Crawler MVP 범위

v1에서는 아래 범위까지만 Crawler MVP의 목표로 제안한다.

```text
- NAVER 상품 URL 1개 기준
- 리뷰 일부 수집
- raw JSON 파일 저장
- 기존 converter/DB insert/RTI 분석 파이프라인에 연결 가능한 형식 확보
```

MVP의 성공 기준은 모든 리뷰를 완전하게 수집하는 것이 아니라, 실제 상품의 일부 리뷰를 확보하여 기존 분석 파이프라인에 전달할 수 있는지 확인하는 것이다.

## 4. v1에서 하지 않을 것

아래 항목은 v1 Crawler MVP 범위에 포함하지 않는다.

```text
- 모든 쇼핑몰 지원
- 로그인 기반 크롤링
- 차단 우회 고도화
- 대량 상품 자동 수집
- 완전한 pagination 자동화
- 이미지 파일 다운로드
- 실시간 운영용 안정성 보장
```

이 항목들은 MVP 검증 후 실제 운영 범위와 우선순위가 확정되면 별도 단계에서 검토한다.

## 5. 수집해야 할 최소 필드

v1 MVP에서는 상품 식별, 리뷰 저장 및 RTI 분석 연결을 위해 아래 필드를 우선 수집한다.

```text
product_id
product_name
product_url
mall
review_id
user_id 또는 author
rating
content
review_date
image_count
images
```

플랫폼 원본 데이터에 일부 필드가 없거나 공개되지 않는 경우 `null`, 빈 배열 또는 대체 필드 사용 여부를 converter 규칙으로 정의해야 한다.

## 6. raw JSON 저장 필요성

크롤링 결과를 즉시 DB에 넣지 않고 raw JSON 파일로 먼저 저장하는 이유는 다음과 같다.

```text
- 원본 데이터 보존
- converter 테스트 가능
- 크롤러 실패/변경 시 원인 추적 가능
- 같은 raw JSON으로 RTI 분석 재실행 가능
- 팀원 간 데이터 형식 공유 쉬움
```

raw JSON을 크롤러와 converter 사이의 중간 결과물로 유지하면 데이터 수집과 분석을 분리해서 검증할 수 있다. 크롤러 또는 외부 응답 형식이 변경되더라도 저장된 원본을 기준으로 변환 규칙과 분석 결과를 다시 확인할 수 있다.

## 7. 실패 시 fallback 전략

크롤러가 실패하더라도 v1 분석 파이프라인 검증이 중단되지 않도록 다음 fallback 전략을 적용한다.

```text
- 크롤러 실패 시 수동 raw JSON 입력 허용
- 샘플 raw JSON으로 converter/RTI 분석 테스트 진행
- 크롤링은 독립 모듈로 분리
- 분석 파이프라인은 크롤러 없이도 검증 가능하게 유지
```

크롤러의 성공 여부와 분석 파이프라인의 검증 가능 여부를 분리하면 외부 쇼핑몰의 변경이나 차단이 발생해도 converter, DB insert, RTI 분석 및 saved RTI 저장 흐름을 계속 검증할 수 있다.

## 8. 팀 협의 필요 항목

아래 항목은 Crawler MVP 구현 전에 팀 협의가 필요하다.

```text
- v1에서 NAVER만 대상으로 할지
- productUrl을 누가 전달할지
- 크롤러 실행 주체가 FastAPI Worker인지 별도 script인지
- raw JSON 저장 위치를 어디로 할지
- 크롤링 실패 시 Job 상태를 FAILED로 볼지
- 리뷰 0개 수집을 실패로 볼지 정상 완료로 볼지
```

특히 리뷰 0개 수집은 실제 리뷰가 없는 경우와 크롤링에 실패한 경우를 구분할 수 있도록 판정 기준과 로그 정보를 함께 정의해야 한다.

## 9. AI 파트 추천 방향

AI 파트에서는 다음 방향을 추천한다.

```text
v1에서는 크롤러 완성도보다 raw JSON → DB insert → RTI 분석 → saved RTI 저장 흐름 검증을 우선한다.
크롤러는 NAVER 상품 URL 1개 기준 샘플 수집 MVP로 제한한다.
크롤러 실패 시에도 수동 raw JSON으로 분석 파이프라인을 검증할 수 있게 한다.
```

이를 통해 외부 플랫폼 의존성이 높은 크롤러 개발과 프로젝트 핵심인 리뷰 신뢰도 분석 흐름을 분리하여 단계적으로 검증할 수 있다.

## 10. 결론

크롤러는 실제 리뷰 데이터를 확보하기 위해 중요하지만, Re:view 프로젝트의 핵심은 수집된 리뷰를 저장하고 신뢰도를 분석하여 saved RTI로 제공하는 흐름이다.

따라서 v1에서는 크롤러를 NAVER 상품 URL 1개와 일부 리뷰 수집 수준의 MVP로 제한하고, raw JSON부터 DB insert, RTI 분석 및 결과 저장까지의 파이프라인 안정화에 집중하는 것이 안전하다.

이 문서는 협의를 위한 전략 문서이며 실제 API, DB schema, Redis/Worker 또는 크롤러 코드를 변경하지 않는다.
